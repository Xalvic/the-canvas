# PostgreSQL: first persistence slice

PostgreSQL is a separate database process. The API uses SQL to store and retrieve
rows in its `boards` table. The records live on disk rather than in the Node
process's Map, so restarting the API or database does not erase them.

This slice persists backend **metadata only**. The free guest canvas still saves
its objects and image Blobs in IndexedDB without login. Users, ownership, cloud
canvas documents, sync, and Prisma are later slices; this is still a local API.

## Run on this machine

PostgreSQL 18.6 binaries and data are in ignored `.postgres/`. It listens on
`127.0.0.1:5433`, uses password authentication, and has a `scribble` database.
The API role `scribble` owns that database but is not a PostgreSQL superuser.
Generated credentials are in ignored `.env`; bootstrap administrator credentials
are in ignored `.postgres/admin.env`. Neither belongs in frontend code or Git.
The database is already initialized; do not rerun setup to start it.

```text
npm run db:status
npm run db:start        # only if stopped; needed after reboot
npm run db:migrate      # safe to repeat
npm run dev:server
```

Run `npm run dev` in another terminal for the canvas. Stop the API before
`npm run db:stop` when finished. The local database does not autostart as a
Windows service. A running API's `/health` remains process liveness only.

## Recreate the local setup on a fresh Windows checkout

1. Run `npm install`.
2. Download the Windows x86-64 ZIP from the official
   [EDB binaries page](https://www.enterprisedb.com/download-postgresql-binaries),
   linked by [PostgreSQL downloads](https://www.postgresql.org/download/windows/).
3. Create `.postgres/` and put the archive at `.postgres/postgresql-windows.zip`.
4. Extract the required folders:

```text
tar -xf .postgres/postgresql-windows.zip -C .postgres pgsql/bin pgsql/lib pgsql/share
npm run db:setup
npm run db:migrate
```

Setup refuses to overwrite an existing `.env` or data directory. It initializes
password authentication, starts the local server, creates the app role/database,
and saves fresh random credentials. It assumes port 5433 is free. If interrupted,
inspect the existing setup rather than deleting its data and rerunning blindly.
These convenience scripts are Windows-specific; the API itself can connect to
an installed PostgreSQL server on other platforms.

For an existing database, copy `.env.example` to `.env`, supply its backend-only
`DATABASE_URL`, and run the migration. The database must already exist and the
role needs permission to create tables. Keep certificate validation enabled
when connecting to a hosted database. This prototype has no remote deployment.
Node 24 loads `.env` for the server and migration scripts; exported environment
variables take precedence. Do not set credentials using a `VITE_` prefix.

## Table and request flow

[`001_create_boards.sql`](../db/001_create_boards.sql) defines:

| Column | SQL type | Purpose |
| --- | --- | --- |
| `id` | `uuid PRIMARY KEY` | Unique board identity, generated by the server |
| `title` | `text NOT NULL` with checks | Board name; API applies strict trim/length validation |
| `created_at` | `timestamptz` | Database-generated creation time |
| `updated_at` | `timestamptz` | Last title change; unchanged for a no-op rename |

The primary key rejects duplicate IDs and provides an index for ID lookups.
Database checks are a second guard behind Zod. The API still returns camelCase
epoch-millisecond timestamps, preserving its HTTP contract. Listing uses
creation time then ID for deterministic ordering, with no pagination yet.

```text
POST /api/boards { "title": "  Ideas  " }
  -> Express parses JSON
  -> Zod validates and trims to "Ideas"
  -> postgresBoards.create executes INSERT with UUID/title parameters
  -> PostgreSQL stores the row and returns its timestamps
  -> API returns 201 { board: ... }

Restart the API -> GET that UUID -> SELECT finds the same stored row
```

[`postgresBoards.ts`](../server/postgresBoards.ts) implements SQL CRUD using `pg`.
`$1`/`$2` placeholders keep values separate from commands. The connection pool
reuses up to five connections. Routes await queries; Express 5 forwards rejected
promises to the existing error handler. There is no silent in-memory fallback.

Rename is one UPDATE statement, avoiding a read/write race. Each CRUD statement
is atomic, but concurrent changed titles use last-writer-wins; there is no
document revision conflict detection or automatic retry. Database unavailability
produces generic 500 responses. Startup requires a reachable, migrated database.

A migration is a versioned schema change. `db:migrate` applies version 1 inside
a transaction and records it in `schema_migrations`. A transaction commits all
steps together or rolls them back on failure. A database lock serializes
concurrent migration runners. Future changes need new numbered migrations;
do not edit version 1 to change a database that already applied it.

The Map in `boards.ts` now serves only as an isolated HTTP-test fixture.

## Verify and next slice

```text
npm test                  # fast tests; database suite skipped without TEST_DATABASE_URL
npm run test:database     # loads local .env and runs the real PostgreSQL suite
npm run typecheck:server
npm run build:server
```

Database tests create and remove only a randomly named schema, leaving normal
board tables alone. `TEST_DATABASE_URL` can override the test connection; the
dedicated test runner otherwise uses local `DATABASE_URL` and fails if absent.
Verified migration repeatability, reconnect persistence, CRUD, database
constraints, parameterized hostile-looking titles, and async error handling.
An HTTP board also survived an actual API process and PostgreSQL process restart.
The existing Postman lifecycle passed 17 requests and 51 assertions on PostgreSQL.

Next: trace INSERT/SELECT together and practice reading this table, then choose
the durable canvas document model (JSONB, object rows, or hybrid). Authentication
and ownership must precede exposing cloud saves. Phase 2 is still in progress.
